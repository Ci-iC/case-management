# GlobalX 法律事务管理系统 v1.1

> 发布日期：2026-04-28（待部署）
> 上一版：v1.0（2026-04-22 上线，定位天弘矿业内部案件台账）
> 本版定位：从"案件台账"扩展为"法律事务管理"，新增**合同审核**整条业务线
> 品牌升级：天弘矿业 案件台账系统 → **GlobalX 法律事务管理系统**

---

## 一、版本定位

- 核心思路：**底层架构升级 + 新业务模块**两件事一起做
- v1.0 是 SQLite + 单用户场景，v1.1 升到 PostgreSQL + 真正的多用户协作 + AI 合同审核工作流
- v1.1 上线后，旧 v1.0 数据通过 migration 自动平滑过渡，不需要手动迁移

---

## 二、底层架构升级

### 2.1 数据库 SQLite → PostgreSQL（同机 Docker）

| 项 | v1.0 | v1.1 |
|---|---|---|
| 数据库 | SQLite 单文件 | PostgreSQL 16（Docker compose） |
| 数据访问 | better-sqlite3 同步 API + 全局 `db` 对象 | Knex 查询构造器 + 连接池 + async/await |
| 服务管理 | `pm2 start` | `npm run db:up` / `npm run dev` 等命令 |
| 备份策略 | 复制 .db 文件 | `pg_dump` 每日 cron（部署文档另写） |

### 2.2 多人协作：乐观锁 + 完整审计

- `cases` 表加 `version` 字段，前端编辑时带上 v 号，PUT 时后端做版本比对
- 后端冲突时返回 `409 + current` 完整字段，前端弹**冲突对话框**：字段级 diff，让用户选「放弃我的修改」或「用我的覆盖」
- 新增 `case_versions` 表：每次案件保存自动写入快照，可追溯
- 新增 `audit_logs` 表：记录所有 login / case 增删改 / 用户增删改 / 设置改动 / 审核创建 等

### 2.3 案件编号唯一约束

- DB 级 `UNIQUE (case_number)`，前端创建/编辑遇到重复时收到 409 + 友好提示

## 三、新业务：合同审核（v1.1 主线）

### 3.1 整体流程

```
业务人员                                      法务（admin）
─────────                                    ─────────
1) 工作台 → 合同审核 → 上传 Word 合同
   选「新合同」起名 / 选「已有合同新版本」
   选审核模型 → 点开始审核
2) 弹窗：选我方立场（甲方/乙方/自定义如"赞助方"）
         选审核幅度（严格/中等/宽松）
3) 后端调 OpenAI（按所选审核模型多节点并行）
   返回固定 JSON 三层级（重大风险/一般风险/优化）
4) 前端把结果渲染为三张表格
5) 业务人员点「发送给法务审核」
   → 站内消息发给 admin（自动带审核意见 + 原合同附件）
                                            6) 法务在消息中心看到，下载原合同修订
                                            7) 上传 Word 修订稿（限 .doc / .docx）
                                            → 关联到该 review 的「法务审核版」
8) 业务人员到合同台账 → 找该合同对应版本
   → 下载「原始版」或「法务审核版」继续修订
```

### 3.2 审核模型（Pipeline）

- 一条审核模型 = N 个并行节点，每个节点独立提示词
- 多节点 `Promise.allSettled` 并行调 OpenAI，单节点失败不阻塞其他
- 输出按层级合并 items，serial_no 重新编号
- admin 后台「**审核模型**」管理：增删节点、上下移动、单独启用/禁用、改提示词、设默认
- 系统出厂自带「通用合同审核」（默认）和「劳动合同审核」两条，可复制修改

### 3.3 审核结果固定 JSON Schema

```json
{
  "review_opinions": [
    {
      "level": "重大风险条款",
      "items": [
        {
          "serial_no": 1,
          "clause_no": "第 X.X 条 / 未编号条款",
          "original_text": "合同原文",
          "revised_text": "可直接替换的修改版",
          "comment": "修改意见和理由",
          "risk_level": "高 / 中 / 低"
        }
      ]
    },
    { "level": "一般风险条款", "items": [] },
    { "level": "优化完善条款", "items": [] }
  ]
}
```

前端三处展示（合同审核页最新结果 + 历史展开 / 合同台账详情 / 消息引用）都用同一个表格组件渲染。表头固定 6 列：**序号 | 条款编号 | 原文 | 修改后原文 | 修改意见 | 风险程度**。

### 3.4 我方立场 + 审核幅度（弹窗参数）

每次发起审核时，必选两个参数：

- **我方立场**：甲方 / 乙方 / 自定义（可填"第三方"/"赞助方"/"承包方"等任意角色）
- **审核幅度**：
  - 严格 — 严格的审核标准，尽可能争取我方利益
  - 中等 — 常规企业法务标准（默认）
  - 宽松 — 只标明显的法律 / 商业风险

后端把这两个参数拼到每个审核模型节点的 system prompt 顶部，引导 AI 视角。实测：同一份合同切换甲方/乙方，AI 给出的问题视角完全翻转。

### 3.5 合同台账（聚合追溯）

- `contracts` 表：用户上传时取一个合同名（同名同上传人 = 同一合同），多次审核 = 多个版本
- 「合同台账」页面：
  - 卡片网格列出所有合同（版本数 / 上次审核时间 / 上传人）
  - 顶部搜索
  - 点开看详情：每版折叠卡（v1/v2/...），最新版默认展开
  - 每版下方两个按钮：「下载原始版」「下载法务审核版」（如果有）
- **审核记录禁删**（合同台账要求完整追溯）

### 3.6 限制：必须 Word 格式

整条链路（业务上传 → AI 审核 → 法务下载修订 → 业务下载继续改）只接受 **.doc / .docx**。从源头保证文件可编辑，避免"业务上传 PDF 法务没法改"的尴尬。

## 四、站内消息

- 业务人员能给法务（admin）发消息，附原合同 + AI 审核意见 + 留言
- 收件人**锁定为法务**，不能自由选（产品决策：避免"站内乱发"）
- admin 给业务人员发消息时**可以**选收件人（管理者下达任务）
- 顶栏邮件图标 + 30 秒轮询未读数
- 消息附件支持多文件上传，单文件 20MB 以内
- **存储优化**：消息附带 review 原文件时，不复制物理文件，引用同一 storage_path（省一半磁盘）
- 删除消息时只删自己上传的附件，引用 review 的不动

## 五、权限模型

三个独立开关，admin 自动全开：

| 权限 | 字段 | 影响 |
|---|---|---|
| 角色 | `users.role` (admin/user) | admin 全权限 |
| 案件管理 | `users.can_view_cases` | 隐藏「案件台账」菜单；无权限调 /api/cases 返回 403 |
| 合同台账 | `users.can_view_contracts` | 隐藏「合同台账」菜单；普通用户只能看自己上传的合同 |

admin 后台「用户管理」加了三个独立切换按钮：💼 案件管理、📁 合同台账、🔑 重置密码、🗑 删除。

## 六、admin 系统设置

「系统设置」面板：

1. **OpenAI 连接配置**
   - API Key（password input + 显隐切换 + 保存后 mask 显示 `sk-t***cdef`）
   - Base URL（留空走 OpenAI 官方；可填代理 / DeepSeek / Moonshot 等兼容端点）
   - 默认模型（如 `gpt-4o-mini`）
   - 「测试连通性」按钮即时验证
   - 改完保存即时生效，**不重启服务**
2. AI 审核提示词管理已**升级到「审核模型」**，系统设置里只留跳转提示

## 七、文件存储

```
server/data/
  reviews/<userId>/<ts>_<filename>           上传的合同文件 + 法务修订版
  attachments/<message_id>/<filename>         消息附件
```

- `reviews/.../<ts>_<filename>` —— 业务上传的原合同
- `reviews/.../<ts>_legal_<filename>` —— 法务上传的修订版
- 消息附件中"引用 review 原文件"的不实际占空间，只在 DB 表里 `review_id` 引用

8GB 服务器估算：1000 份合同/年 × 平均 5MB × 1 份（不重复存） ≈ 5GB / 年。

## 九、依赖与部署

新增 npm 依赖（相对 v1.0）：

| 包 | 用途 |
|---|---|
| `pg` | PostgreSQL driver |
| `knex` | SQL 构造器 + migration 工具 |
| `multer` | 文件上传中间件 |
| `mammoth` | .docx 解析 |
| `word-extractor` | .doc 老格式解析 |
| `pdfjs-dist` | PDF 解析（备用，当前路由层禁用了 PDF） |

部署增量步骤（基于 v1.0 已部署环境）：

1. 安装 Docker（如未安装）
2. `npm install` 装新依赖
3. `cp .env.example .env`，填入 `DATABASE_URL` / `JWT_SECRET` / `ADMIN_*`
4. `npm run db:up` 启动 PG 容器
5. `npm run db:migrate` 跑 migration（会建所有表）
6. `npm run db:seed` 创建初始 admin
7. 进入「系统设置」配置 OpenAI API Key
8. 启动后端：`pm2 start server/index.js`
