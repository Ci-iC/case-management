# GlobalX 法律事务管理系统 v1.3.2

> 发布日期：2026-05-11
> 上一版：v1.3.1（2026-05-08，合同审批 + AI 摘要）
> 本版定位：**安全加固 + 删用户 bug 治根**。无新业务功能，纯修复 + 防护。

---

## 一、为什么发这一版

v1.3 上线后暴露两个问题：

1. **删用户报错**：只要那个用户在审批流里出现过（发起人/审批人/加签人），就删不掉，PG 报 `null value in column "assignee_id" of relation "approval_steps" violates not-null constraint`。
2. **安全风险盘点**发现几处生产硬伤：
   - JWT 签名密钥默认值 `dev-secret-change-me`，没强制要求生产环境覆盖
   - CORS 完全开放（任何域名都能调 API）
   - 登录接口没有频率限制（可被暴力破解）
   - JWT 有效期 7 天，过长

v1.3.2 一次性把这些都处理掉。

## 二、用户删除：改成"软删除"

### 改造逻辑

| 维度 | v1.3 | v1.3.2 |
|---|---|---|
| 删除方式 | 真的从 users 表删行 | 设置 `deleted_at = now()`，行保留 |
| 历史记录里的"经办人/审批人" | 删后变 NULL，前端显示空白 | **照常显示原 username/display_name**（外键 JOIN 仍能查到） |
| 用户名能否复用 | 不能（unique 卡死） | 可以（unique 约束改成 partial，仅约束未删除用户） |
| 在途审批怎么办 | 删不了 → 卡死 | **整体作废**，对应合同退回起草中，经办人重新发起即可 |
| 已完结审批 | — | **保留**，审批记录里的人名照常显示 |
| 被删用户的登录会话 | — | **立刻踢下线**（token_version+1） |
| 被删用户重新登录 | — | 被拒绝（login 接口过滤 deleted_at） |

### 业务上的影响

- 删 Jack 这种 admin：他参与的**在途**审批整条作废，合同状态回到"起草中"，对应经办人会在合同审批页看到合同重新可以发起审批
- 删除是不可逆的（界面上没有"恢复"按钮）；如有需要可直接在 DB `UPDATE users SET deleted_at = NULL WHERE id = ?` 手动恢复
- 已删除用户的用户名**可以**被新用户复用（比如 Jack 离职后又入职，可以重新建一个叫 Jack 的账号，原来那个 Jack 的所有历史记录依然显示"Jack"）

## 三、产品决策修正：admin 角色重新定位

v1.3 文档里把 admin 定位为"法务"。实际业务用下来发现这个定位错了：

| 角色 | v1.3 原定位 | **v1.3.2 修正** |
|---|---|---|
| `superadmin` | 系统管理员 + 第一审批人 | **法务 + 系统管理员 + 第一审批人**（法务工作归 superadmin） |
| `admin` | 法务 | **公司高管 / 领导**，业务方角色之一 |
| `user` | 普通业务人员 | （不变） |

### 由此带来的改动

- 「合同审核」页面现在对 **admin 显示**「发起审核 / 智能审核」模式切换 + 「发送给法务审核」按钮。原来这些 UI 对 admin 是隐藏的（因为认为 admin 自己就是法务，不需要再发给法务）。
- admin 走「发送给法务审核」时，**收件人自动锁定为 superadmin**。
- 「合同审核页（业务方）」这个章节标题更准确的理解：**业务方 = user + admin**（superadmin 才是法务）。
- 合同审批：admin 本就能发起（v1.3 已支持），现在的定位下这条路径符合产品语义，无需改动。

### 法务工作权限严格收紧到 superadmin

法务工作（接收审核 + 修订版上传 + 直接通过）**只允许 superadmin**：

- 后端 `POST /api/reviews/:id/legal-revision` 权限从 `requireAdminOrAbove` 改为 `requireSuperAdmin`
- 后端 `POST /api/reviews/:id/legal-approve` 权限同上
- 前端「消息中心」的「法务答复区」（上传修订版 / 直接通过两个按钮）**只对 superadmin 显示**
- 前端「发送给法务审核」对话框自动选收件人：**严格只挑 superadmin**，不再回退 admin（系统保证至少有一个 superadmin 账号在）

## 四、安全加固清单

### 1. JWT 密钥强制环境变量

启动时检查 `process.env.JWT_SECRET`：

- 未设置 → **直接抛错拒绝启动**
- 等于历史占位字符串（`dev-secret-change-me` / `change-me-to-a-long-random-string`）→ **同上**

部署必做：在 `.env` 里设置一个强随机值。生成方式（任何能跑 node 的机器上）：

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

把输出粘到 `.env` 的 `JWT_SECRET=` 后面。

### 2. JWT 有效期 7 天 → 1 天

`TOKEN_TTL` 从 `7d` 改 `1d`。意味着每个用户最多每天重新登录一次。配合"单设备登录"机制，token 泄露的风险窗口大幅缩短。

### 3. CORS 收紧

原来：`app.use(cors())`（全开放，任何域名都能调）
现在：读环境变量 `CORS_ORIGIN`

- 留空（推荐）= 同源部署，浏览器只能从你的域名访问 API
- 多个域名英文逗号分隔，如 `CORS_ORIGIN=https://a.example.com,https://b.example.com`

### 4. 登录限流

新增 `express-rate-limit` 依赖。`/api/auth/login` 接口：同 IP 15 分钟内最多 10 次失败，超过返回 429。

### 5. trust proxy

`app.set('trust proxy', 1)`，让 express 信任 nginx 等前置代理转发的 X-Forwarded-For 头，限流才能拿到真实客户端 IP（否则所有请求 IP 都是 nginx 自己 127.0.0.1）。

## 七、HTTPS 部署（手动核对一遍）

代码层面没有 HTTPS 相关改动，HTTPS 是 nginx 那一层的事。运维配好后请核对：

- [ ] 80 端口强制跳转到 443
- [ ] SSL 证书有效（阿里云免费证书 / Let's Encrypt 都可）
- [ ] nginx 反代到 localhost:3000（或 docker 内端口）
- [ ] 移动端、桌面浏览器访问 `https://你的域名/` 不出现警告

## 八、留给 v1.4 / 后续的事

| 项 | 优先级 | 说明 |
|---|---|---|
| 密码强度规则 | 中 | 当前最少 6 位，建议 8+ 含数字字母 |
| 用户改密码后踢下线 | 中 | 当前 change-password 不递增 token_version，会让"密码泄露 → 改密"场景下旧 token 仍能用 7 天 → 调整为 1 天后窗口缩短，但仍非零 |
| 错误信息脱敏 | 低 | 生产模式下 `err.message` 可能含数据库 schema 信息 |
| 上传文件 magic-bytes 校验 | 低 | 当前只看扩展名，伪装风险低但存在 |
| 删人快照 | 低 | 软删除已经解决了大多数场景；如要支持"硬删除"（合规要求时），需要在删之前把 username/display_name 快照写入相关表的新字段 |
| 审批超时提醒 | — | v1.4 既定 |
| 并行审批 / 模板 / OCR / 合同到期 / 审计 UI | — | v1.4 既定 |

## 九、给下次会话的快速上手

如果你（或新会话的 Claude）在 v1.3.2 之后继续做事：

1. **业务全貌**：以 `docs/版本说明 v1.3.md` 为基础 + 本文档（v1.3.2 修正了角色定位、加了安全和软删除）
2. **本版新增的关键概念**：
   - `users.deleted_at` —— 任何读 users 表的地方都要 `WHERE deleted_at IS NULL`（已在 6 个地方加好；新增接口要记得带上）
   - **角色定位修正**：v1.3.2 起 admin 是高管/领导（业务方角色），不是法务；superadmin 才是法务
3. **部署 v1.3.2 时的最高优先事项**：`.env` 里 `JWT_SECRET` 是不是真的设了强值（启动时会 fail-fast，但部署前最好直接检查一遍 `.env`）
