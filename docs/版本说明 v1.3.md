## 一、版本定位

| 维度 | v1.1 | v1.3 |
|---|---|---|
| 合同生命周期 | 没有状态概念，"过法务"就完事 | **状态机：起草中 / 审批中 / 待签署 / 已签署** |
| 合同标识 | 用户取名，按 `(name, created_by)` 去重 | **系统自动编号 `YYYY-HT-NNNN`，全局唯一**；名称允许重复 |
| 角色 | admin / user 两层 | **superadmin / admin / user 三层** |
| 同账号多设备 | 同时登录互不影响 | **后登录顶掉前登录**，旧 token 自动失效 |
| 审核草稿 | 每次 AI 审核立即入库 | **草稿态（is_draft）**，未发法务则 24h 后自动清理 |
| 法务答复 | 必须上传修订版 | **支持"无需修订直接通过"**（带留言） |
| 合同审批 | 无 | **完整流程引擎**：发起 → 超管分派 → 多级审批 → 通过/驳回/加签 → 用印 |
| AI 合同摘要 | 无 | 发起审批时基于**清洁版**自动生成（双方/标的/金额/期限），prompt 可在系统设置里调 |
| 站内信 | 仅消息中心人工发 | **审批每次流转自动通知当前节点 assignee**，带"跳转到审批"按钮 |

## 二、合同生命周期（状态机）

```
   ┌───────────┐    发起审批     ┌───────────┐    全部审批通过    ┌───────────┐    上传用印版    ┌───────────┐
   │ drafting  │ ─────────────► │ approving │ ─────────────────► │pending_seal│ ─────────────► │  sealed   │
   │  起草中   │                │  审批中   │                    │  待签署   │                │  已签署   │
   └───────────┘                └───────────┘                    └───────────┘                └───────────┘
        ▲                            │
        │     驳回-重新发起           │
        └────────────────────────────┘
```

- `contracts.status` 字段直接存这 4 态（不依赖联表推导，过滤简单）
- 状态变更只在 `server/routes/approvals.js` 里发生，所有事务都同时更新 contracts.status
- 合同台账列表顶部 4 个 tab 直接按 status 过滤

## 三、合同审批流程（核心业务）

### 3.1 角色与节点

```
经办人发起 → step_index=1 (超管) → step_index=2..N (后续审批人) → final-initiator (经办人传用印版)
                                        │
                                        ▼ （任意 approver 节点可以加签）
                                   consultee 子节点
```

| 节点类型 | step_type | 职责 | 操作选项 |
|---|---|---|---|
| 主链审批人 | `approver` | 审批 | 通过 / 驳回 / 加签 |
| 加签咨询人 | `consultee` | 临时咨询，不影响主链 | 仅"提交意见" |
| 最终经办人 | `final-initiator` | 全部通过后上传用印版；驳回-到经办人节点时也回这里 | 上传用印版 / 重新提交 |

### 3.2 强制约束

- 第一审批人 (`step_index=1`) **必须**是 superadmin
- 后续审批人列表由超管在第一次"通过"时填写（按顺序，可空）
- 同一合同同时只能有 1 条进行中的 approval（`status='pending'`）
- 发起审批时合同必须满足：
  - `contracts.status='drafting'`
  - 有过法务审核：最近一次 review 满足 `reviewed_storage_path IS NOT NULL OR legal_approved=true`
  - 必须上传**清洁版**或选择沿用现有清洁版

### 3.3 审批操作语义

**通过**（仅 approver 节点）
- 当前 step.status='approved'
- 流转到下一个 approver（按 step_index 升序）；若没有下一个 → 流转到 final-initiator，contract.status 变 `pending_seal`
- 超管首次通过时必须填后续审批人列表（可空 = 直接走经办人）
- 自动通知下一节点 assignee

**驳回 - 返回当前节点**
- 当前 step.status='rejected'，approval.status 仍 `pending`
- approval.current_step_id → final-initiator
- 经办人在合同审批页看到"重新提交"按钮 → 提交后**直接跳回驳回人**（不重走中间已通过的人）
- 经办人 resubmit 时**可选**替换清洁版（不强制）
- 自动通知经办人"被驳回，请修改重提"

**驳回 - 重新提起审批**
- 当前 step.status='rejected'，approval.status='rejected' 关闭本轮
- contract.status 退回 `drafting`，contract.approval_id 清空
- 经办人需要在合同审批页**重新发起**新一轮（可上传新清洁版或沿用旧的）
- 自动通知经办人"本轮已驳回，请重新发起"

**加签**（仅 approver 节点）
- 选 1 个加签人，创建临时 `consultee` 子步骤（`parent_step_id` 指向加签人主步骤）
- 控制权转给加签人，但加签人**只能"提交意见"**，没有通过/驳回选项
- 加签人提交后控制权回到加签人主步骤，加签人继续做通过/驳回/再加签
- 自动通知加签对象 + 提交后通知加签人

**上传用印版**（仅 final-initiator 节点，且不在被驳回状态）
- 经办人上传 PDF/JPG/Word
- contract.sealed_* 填充，contract.status='sealed'，contract.approval_id 清空（历史 approval 仍在 approvals 表）
- approval.status='completed'

### 3.4 流转通知

每次状态流转后给当前节点 assignee 自动 INSERT 一条 messages（`approval_id` 字段非空）。前端识别后在消息详情显示**"跳转到审批"按钮**。

文案模板见 `server/routes/approvals.js` 的 `buildNoticeBody()`。

## 四、AI 合同摘要

- 发起审批时**异步**（不阻塞接口返回）调用 OpenAI 生成
- 基于**清洁版**文本（不是原合同也不是法务版）
- 输出 4 段：双方主体 / 合同标的 / 金额与支付节奏 / 关键期限
- 存 `contracts.summary` + `summary_generated_at`
- prompt 存 `app_settings.contract_summary_prompt`，超管在「系统设置」里可改，下次发起审批生效
- 切换清洁版（重新发起 / resubmit 时换文件）会清空 summary 让其重新生成

## 五、数据模型（v1.3 完整字段）

### 5.1 `contracts`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | |
| **code** | text UNIQUE NOT NULL | `YYYY-HT-NNNN`，年内序号、全表唯一 |
| name | text | 合同名（人类可读，**允许重复**） |
| description | text | |
| **status** | text | `drafting` / `approving` / `pending_seal` / `sealed` |
| **approval_id** | uuid → approvals.id | 当前活跃 approval（pending_seal 时也保留；sealed 后清空） |
| **summary** | text | AI 摘要，4 段纯文本 |
| summary_generated_at | timestamptz | |
| **clean_filename / clean_storage_path / clean_size_bytes / clean_mime_type / clean_uploaded_at / clean_uploaded_by** | | 清洁版文件元数据 |
| **sealed_filename / sealed_storage_path / sealed_size_bytes / sealed_mime_type / sealed_at / sealed_by** | | 用印版文件元数据 |
| **approval_started_at** | timestamptz | （v1.2 加，已弃用，保留兼容） |
| created_by | text → users.id | 经办人 |
| created_at / updated_at | timestamptz | |

### 5.2 `approvals`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | |
| contract_id | uuid → contracts.id | CASCADE |
| initiator_id | text → users.id | 经办人 |
| status | text | `pending` / `completed` / `rejected` |
| current_step_id | uuid → approval_steps.id | 当前等待操作的步骤；流程结束后为 null |
| initiation_note | text | 经办人发起说明 |
| created_at / updated_at / completed_at / rejected_at | timestamptz | |

### 5.3 `approval_steps`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | |
| approval_id | uuid → approvals.id | CASCADE |
| step_index | int | 主链 1..N，最终经办人节点 = 999，consultee = NULL |
| parent_step_id | uuid → approval_steps.id | 仅 consultee 节点用，指向其加签来源主步骤 |
| step_type | text | `approver` / `consultee` / `final-initiator` |
| assignee_id | text → users.id | |
| status | text | `pending` / `approved` / `rejected` / `skipped` |
| comment | text | 该步骤上一次操作的意见（最新覆盖；历史在 actions 里） |
| actioned_at / created_at | timestamptz | |

### 5.4 `approval_actions`

每次用户对 approval 的操作都落一条审计记录（不可变）。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | |
| approval_id | uuid | CASCADE |
| step_id | uuid → approval_steps.id | 操作时所在步骤 |
| actor_id | text → users.id | |
| action | text | `submit` / `approve` / `reject_to_step` / `reject_to_start` / `add_consultee` / `submit_consultation` / `resubmit` / `upload_seal` |
| comment | text | 操作意见 |
| target_step_id | uuid | 驳回 / 加签时指向的目标步骤 |
| payload | jsonb | 例如超管通过时填的 `nextApprovers: [...]` |
| created_at | timestamptz | |

### 5.5 `case_reviews`（v1.3 关键字段）

| 字段 | 类型 | 说明 |
|---|---|---|
| **is_draft** | boolean | true=AI 审核完未发法务的草稿，24h 后自动清理 |
| **legal_approved** | boolean | true=法务点过"无需修订直接通过"。`reviewed_storage_path 非空 OR legal_approved=true` 即视为"过法务" |
| reviewed_filename / reviewed_storage_path / reviewed_by / reviewed_at | | 法务上传修订版的元数据 |

### 5.6 `messages`（v1.3 关键字段）

| 字段 | 类型 | 说明 |
|---|---|---|
| review_id | uuid → case_reviews.id | 关联 review，前端显示"AI 审核意见"折叠区 |
| **approval_id** | uuid → approvals.id | 关联 approval，前端显示"跳转到审批"按钮 |

`message_attachments.review_file_kind` 三态：
- `'original'` → 下载时跟到 `case_reviews.uploaded_storage_path`（业务方上传的原合同）
- `'legal'` → 下载时跟到 `case_reviews.reviewed_storage_path`（法务版）
- `null` → 普通自传附件，用 `message_attachments.storage_path`

### 5.7 `users`（v1.2/1.3 关键字段）

| 字段 | 说明 |
|---|---|
| role | `superadmin` / `admin` / `user` 三层（v1.2 拆分） |
| **token_version** | 每次登录 +1，前端 token 里塞上次 version；旧 token 自动失效（v1.2 单设备登录） |
| can_view_cases / can_view_contracts | 普通 user 的两个独立权限开关 |

## 十、依赖与部署

**没有新增 npm 依赖**（v1.3 全部用现有 stack：Express / Knex / multer / OpenAI / mammoth）

**部署增量**（基于 v1.1 已部署环境）：

```bash
# 1. 拉新代码（zip 模式：双击「打包部署.bat」 → OSS → wget → unzip）
# 2. 装依赖（如有）
npm install --omit=dev --no-audit --no-fund
# 3. 跑迁移（011~015 一并跑）
npm run db:migrate
# 4. 重启
pm2 reload case-mgmt
```

> ⚠️ migration 011 会**清空** message_attachments / messages / case_reviews / case_versions / contracts / audit_logs（用户在 v1.2 改造时确认了所有数据都是测试数据）。如果你的环境有要保留的真实数据，**先备份 PG**。

> ⚠️ Windows 本地 PG 端口要用 5500（5432 在 Hyper-V 保留段内）；云上 Linux 5432 没问题，docker-compose.yml 里写的就是本地 5500，部署到云**不要带这个改动到 docker-compose.yml**。

## 十一、留给 v1.4 的事

- **审批超时提醒**：当前节点超过 N 天没操作，发提醒消息
- **批量审批 / 多审批人并行**：当前是严格线性，但有些场景需要并行（"任意 2 人通过即可"）
- **审批模板**：常用合同类型固定一组审批人顺序，发起时一键套用
- **OCR**：扫描版 PDF（v1.1 留下来的）
- **合同到期提醒**：合同附履行期限 → 临近时通知经办人
- **审计日志查看 UI**：当前 audit_logs 写得很全，但前端没有专门的查看页
