# v1.1 M4 方案：AI 审核 + 站内消息

写于 2026-04-27。M4 范围比 M3 大很多，先把表结构 / API / UI 流程对齐，避免返工。

---

## 0. 业务流程目标

```
业务人员                                      主管 (wells)
─────────                                    ─────────
1) 在系统里上传一份法律文件（合同/协议/...）
2) 点「AI 审核」→ 后端调 OpenAI，
   用一段固定提示词产出纯文字审核意见
3) 看完审核意见，认为有价值 →
   点「回传给主管」→ 弹消息编辑器，
   预填：原文件、审核意见、关联案件
   写一段留言 → 发送
                                          4) 在「消息中心」看到收件
                                          5) 展开看：留言全文 + 审核意见
                                             + 下载原文件 + 跳转关联案件
```

不做（v1.2 再说）：邮件通知、桌面推送、未读小红点、消息@提及。

## 1. 数据模型（新增 3 张表）

### 1.1 `case_reviews`（AI 审核记录）

| 列 | 类型 | 说明 |
|---|---|---|
| id | uuid | PK |
| case_id | text → cases.id (可空) | 关联案件，未关联也能审 |
| uploaded_filename | text | 用户上传的原始文件名 |
| uploaded_storage_path | text | 后端存储相对路径 |
| uploaded_size_bytes | bigint | 文件大小 |
| uploaded_mime_type | text | MIME 类型 |
| prompt_version | text | 用了哪个版本的提示词（便于追溯） |
| review_text | text | AI 返回的纯文字审核意见 |
| model | text | 用的哪个 AI 模型 |
| created_by | text → users.id | 谁发起的审核 |
| created_at | timestamptz | |

一个 case 可以审多次（合同改完再审），按时间倒序展示。

### 1.2 `messages`（站内消息）

| 列 | 类型 | 说明 |
|---|---|---|
| id | uuid | PK |
| sender_id | text → users.id | |
| receiver_id | text → users.id | |
| body | text | 留言正文 |
| case_id | text → cases.id (可空) | 关联案件 |
| review_id | uuid → case_reviews.id (可空) | 如果是从审核回传的，引用 |
| is_read | boolean default false | |
| read_at | timestamptz (可空) | |
| created_at | timestamptz | |

> 为什么 review_id 而不是把 review_text 复制进 body？因为审核意见可能很长（几千字），不希望消息表臃肿；引用还能保留追溯链。

### 1.3 `message_attachments`（消息附件）

| 列 | 类型 | 说明 |
|---|---|---|
| id | uuid | PK |
| message_id | uuid → messages.id ON DELETE CASCADE | |
| filename | text | 原始文件名 |
| storage_path | text | 后端相对路径 |
| size_bytes | bigint | |
| mime_type | text | |
| created_at | timestamptz | |

附件存储约定：`server/data/attachments/<message_id>/<filename>`，已在 `.gitignore`。

## 2. 后端 API

### 2.1 审核相关

```
POST   /api/reviews                  上传文件 + 触发 AI 审核
                                     multipart: file, caseId? , model?
                                     返回 { review: {...} }

GET    /api/reviews?caseId=xxx       某案件的审核历史
GET    /api/reviews/:id              单条审核详情（含 review_text 全文）
GET    /api/reviews/:id/file         下载原始上传文件（流式）
DELETE /api/reviews/:id              删除（仅创建人或 admin）
```

### 2.2 消息相关

```
GET    /api/messages?folder=inbox|sent          收件箱 / 发件箱
GET    /api/messages/:id                        详情（含附件元数据 + review 引用）
POST   /api/messages                            发送
                                                multipart:
                                                  receiverId, body, caseId?, reviewId?,
                                                  attachments[] (file 列表)
POST   /api/messages/:id/read                   标记已读
DELETE /api/messages/:id                        删除（仅发送方/接收方）
GET    /api/messages/unread-count               未读数（顶栏 badge 用，先返回，前端不强制显示）
GET    /api/messages/:id/attachments/:aid       下载附件
```

### 2.3 用户相关（已有 `/api/users` 改一点）

`GET /api/users` —— 让前端能拿到用户列表用于"选收件人"下拉框。已存在，可能需要返回字段微调。

## 3. AI 审核提示词配置

按你的意思，"通过提示词来修改"。两种放法：

**方案 A：写在前端 SettingsModal，存 localStorage**
- 优点：你随时可以改，不用动代码
- 缺点：写死在你浏览器，业务人员看不到也改不了
- 适合：提示词由你独家维护

**方案 B：写在后端 .env 或 DB，所有人共享**
- 优点：业务人员触发审核也用同一份提示词
- 缺点：业务人员触发审核需要后端帮他们调 OpenAI（消耗你的 API Key）

**审核流程的 API Key 谁出？**
- 现状：`extractCaseFromFiles` 是前端直接调 OpenAI，用 SettingsModal 里的 API Key —— 即每个用户用自己的 Key
- 如果业务人员要触发审核，要么他们自己填 Key（每人一份，烦），要么后端代调（你的 Key 给所有人用）

**我倾向：**
- AI 审核也走前端直调，业务人员要用就自己在 Settings 填 Key
- 提示词放前端 SettingsModal，但**默认值写死在代码里**，初次进入有合理的默认提示词，业务人员一般不动
- 这样架构最简单，不用动后端的 OpenAI 集成

⚠️ **决策点 1**：是否同意上面这个方案？还是希望后端代调（你出 Key）？

## 4. 前端 UI 改造

### 4.1 新增「AI 审核」入口
- 在某个案件详情页加 `「AI 审核」` Tab，或者侧边栏加「AI 审核中心」一级菜单
- ⚠️ **决策点 2**：哪种？我倾向放在案件详情里，因为审核总是跟具体案件挂钩

### 4.2 审核界面
- 拖拽 / 点击上传一个文件（PDF / Word）
- 选模型（沿用 SettingsModal 里的模型选项）
- 点「开始审核」→ 进度提示 → 显示 AI 输出的纯文字意见（可折叠/展开）
- 历史审核记录：列表，点击展开看全文
- 每条意见底部按钮：「回传给主管」、「删除」

### 4.3 「回传给主管」对话框
- 收件人（默认填主管 wells，下拉可改）
- 留言文本框
- 关联案件（如果是从案件详情进入的，自动填）
- 自动附带：原文件 + 审核意见（作为引用，不是附件）
- 「发送」按钮

### 4.4 顶栏「消息」入口
- 顶栏右上角加一个图标（lucide `Mail`），点开进消息中心
- 未读数 badge：先做接口，前端先不强制显示，留接口给 v1.2

### 4.5 消息中心页面
- 左：收件箱 / 发件箱切换
- 中：消息列表（发件人 / 时间 / body 摘要 / 有附件图标）
- 右：选中消息的详情面板
  - 发件人 + 时间
  - 关联案件（点击跳转）
  - 引用的审核意见（折叠展开）
  - 留言全文
  - 附件列表（点击下载）
  - 删除按钮

## 5. 角色 / 权限

现状：`users.role` 是 `admin | user`，但代码里没做权限隔离（除了路由 `requireAuth` 检查登录）。

M4 临时简化：
- 任何登录用户都能上传文件触发 AI 审核
- 任何登录用户都能给任意其他用户发消息
- 不做"业务人员只能看自己案件"这种 RBAC

⚠️ **决策点 3**：这样是否够用？还是 M4 必须做权限隔离？我倾向暂时不做，等系统跑起来用户增长了再说。
